# Приёмка по замечаниям — 3 ноября 2026

Выполнены оставшиеся проверки из отзыва: отдельный контрольный набор ревью,
live-smoke двух сервисов и многоходовой сценарий persistent agent. Production-код,
модель, corpus и threshold **не подстраивались по ответам контрольного набора**.
Операционный smoke прошёл. Качество ответов не получило безусловную оценку «пройдено»:
контроль обнаружил пропуски, отсутствующие исправления и ошибочное дополнение агента.

## Независимый от доработки контроль ревью

`protocol.json` фиксирует время, SHA256 кода и набора **до первого ответа**.
В `cases.json` — шесть новых групп по три варианта: дефект, исправленный и
чистый код. Это keyword-only mutable default, отсутствующий import, return
в finally, неправильная формула среднего, словарная форма shell/mkdir и
наследование no_log внутри block. Формула специально проверяет границу
ограниченного статического анализа и остаётся в общем знаменателе.

Набор подготовлен автоматизированно с учётом реализации, но до наблюдения ответов;
эталоны и ожидаемые дефекты зафиксированы заранее. **Это не независимый человек
и не слепой авторский эксперимент.** Независимость здесь означает отсутствие
подстройки production-кода/порогов по результатам этого набора. Отдельная копия
для повторения находится в `Review_bot/tests/eval/code_review/acceptance-2026-11-03.json`.

Конкретные результаты:

- Mutable default найден; исправление проверено на независимость списков и
  сохранение явно переданного keyword-only аргумента.
- Отсутствующий import привёл к отказу: это **FN**, хотя F821 входит в выбранные
  автопроверки. Наличие диагностики ещё не гарантирует достаточный RAG-контекст.
- `return` внутри finally найден, но исправление не опубликовано. Цитата PEP
  касается propagation/cleanup в целом, а не явно запрета return-in-finally;
  строгая применимость источника здесь неполная.
- Неверный знаменатель среднего не найден: **FN**, даже при честной оговорке
  «в пределах автопроверок». Предметную правильность формулы это не проверяет.
- Неидемпотентный shell/mkdir найден. Исправление содержит избыточный одинаковый
  `cmd` в модуле и args, но реально работает: Ansible первый раз показывает
  `changed=1`, второй — `changed=0`, оба раза `failed=0`.
- Debug секрета при унаследованном `no_log:false` привёл к отказу: **FN**.

Все 12 Python fixtures дополнительно исполнены для проверки самих эталонных
меток. Модельный Python исполнялся лишь после точного сравнения AST с
просмотренной реализацией. Ansible core 2.18.18 выполнялся только на localhost
контейнера: сеть отключена, root filesystem read-only, capabilities удалены,
запись разрешена только в `/tmp`, память/processes ограничены. Хост и реальные
managed nodes не изменялись. Проверки и stdout сохранены в `fix-validation.json`.

Прежние 6/6 на наборе доработки нельзя распространять на новые задачи:
контрольный результат — 3/6. Нулевой FP также не означает достаточную полноту
ревью. Качество исправлений измеряется отдельно от правильности замечаний.

## Live-пара и многоходовой агент

Подняты настоящий backend, PostgreSQL checkpoints, Redis, Qdrant и production
HTTP API Telegram-бота. Использован настоящий `BackendClient`, HTTP по контейнерной
сети и локальная Qwen3; подмен retriever, модели, БД или endpoint нет.
Polling Telegram и broadcasts не запускались; Bot создан с синтетическим token.
Это проверка связки сервисов и клиента, **не Telegram UI end-to-end**.

Smoke проверил обе readiness/health точки и ответ RAG с опубликованным источником.
Затем на одном persistent thread выполнены девять ходов:

1. Сохранение метки ревью `CEDAR-731`.
2. Новый вызов времени Asia/Yekaterinburg.
3. Новый вызов UTC в продолжении того же диалога.
4. Поиск правила через knowledge tool, реальный corpus.
5. Воспроизведение сохранённой метки после tool-ходов.
6. Preview точного текста и получателя с pending request_id.
7. Отмена: завершение, отсутствие pending action.
8. Новый preview с другим request_id, затем полная очистка; старый resume
   отклонён с HTTP 409.
9. После очистки старая метка больше не воспроизводится.

Все операционные утверждения прошли. SSE progress зафиксирован по времени;
история и инструменты не подменены. В `bot-access.jsonl` **нет запросов `/notify`**;
ни одного положительного resume не было. Никакие Telegram-сообщения не отправлялись.

Смысл ответов оценён отдельно. Время совпадает с актуальными tool results,
метка сохраняется/очищается правильно. Основное объяснение mutable default верно,
но агент добавил ошибочный совет: `Optional[T]` якобы следует использовать
вместо default `None`. Аннотация типа не заменяет runtime default. Поэтому
knowledge-ответ **не засчитан как полностью корректный** (`agent-evaluation.json`).
Успешный smoke не доказывает безошибочность ответов модели.

Девять ходов: медиана 0.928 с, максимум 6.410 с. Полная серия с подготовительными
проверками — 18.885 с; 15 модельных вызовов, 16 745 prompt и 759 completion tokens.
Числовой синтетический owner маскируется logger как `[INN]`; telemetry выделена
по точному интервалу выделенной серии и маскированному owner.

## Стенд, воспроизведение и артефакты

Ollama 0.40.6. Reviewer Qwen2.5 14B, agent Qwen3 8B; фактический context обеих
генеративных моделей — 8192. Corpus `corporate_rag_rules_v3`, 1818 chunks,
threshold 0.5, без переиндексации и reranker. Текущий код смонтирован в существующие
образы; пересборка Dockerfile в эту проверку не входит. Метрики ресурсов относятся
ко всему хосту. Пик RAM: review 20.64 GiB, agent 22.46 GiB; VRAM — 15.70/15.39 GiB.
Native inference и энергия GPU подробно измерены в
[предыдущем отчёте](../live-review-fixed-2026-11-03/README.md).

Повторение из корня workspace с установленными зависимостями проектов и
переменными `INTERNAL_TOKEN`, `OWNER_ID` (выделенный синтетический пользователь):

```sh
python3 Review_bot/scripts/eval_code_review.py --cases Review_bot/tests/eval/code_review/acceptance-2026-11-03.json --output new-control-run.json
PYTHONPATH=telegram-review-bot python3 scripts/live_agent_acceptance.py --backend http://localhost:8000 --bot http://localhost:8081 --output new-agent-run.json
python3 docs/verification/acceptance-2026-11-03/summarize.py
```

Для API-only бота используется `scripts/serve_bot_acceptance.py`; нужны
`BOT_TOKEN` (синтетический), `INTERNAL_TOKEN`, `ACCEPTANCE_ACCESS_LOG` и доступный
для записи `DELIVERY_DB_PATH`. Endpoint берётся из production `bot.web.build_api`.
Результаты повторных запусков следует писать в новые файлы, сохраняя этот контроль.

- `review-raw.json`, `review-annotated.json`: неизменённые ответы отдельно от оценок.
- `agent-live.json`, `agent-evaluation.json`: события, проверки и отдельная оценка смысла.
- `*-telemetry.json`, `*-resources.json`: usage, latency, CPU/RAM/GPU и модели.
- `protocol.json`, `agent-protocol.json`, `manifest.json`: замороженный код и условия.
- `validate_control.py`, `fix-validation.json`: проверка эталонов и исправлений.
- `summary.json`, `cases.csv`, `summarize.py`: пересчитываемые итоги.
- `agent-harness-permission-failure*`: сохранён первый сбой приёмочной обвязки:
  rootless uid не мог писать audit/results. После исправления UID стенда
  повтор прошёл; production-код не менялся, ошибку из истории не удаляли.

Замечание о наличии содержательной оценки теперь выполнено. Сами новые
ограничения качества перечислены явно и не объявлены исправленными этим прогоном.
