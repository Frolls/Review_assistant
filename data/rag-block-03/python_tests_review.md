# Python Tests Review

Тесты в PR должны покрывать поведение, которое реально изменилось. Если автор меняет ветвление, обработку ошибок, формат ответа или контракт API, ревьюер должен искать тест на новую ветку и на регрессию старого поведения.

Unit-тесты должны быть детерминированными. Нельзя зависеть от реального времени, случайных значений, сети или внешней базы без фикстур и изоляции. Для времени используется freeze/fake clock, для сетевых клиентов - mock или test double.

Хороший тест проверяет наблюдаемое поведение, а не внутреннюю реализацию. Если тест ломается при безопасном рефакторинге приватной функции, он слишком тесно связан с деталями реализации.

Для багфикса нужен тест, который падает до исправления и проходит после него. Если PR чинит production-инцидент без регрессионного теста, ревьюер должен попросить добавить минимальный воспроизводимый сценарий.

Интеграционные тесты нужны для контрактов между слоями: FastAPI route и service, repository и database, serializer и schema, retry/cache и внешний клиент. Такие тесты должны быть меньше числом, но покрывать самые дорогие ошибки.
