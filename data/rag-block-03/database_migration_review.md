# Database Migration Review

Миграция базы данных не должна держать долгую exclusive lock на большой таблице в рабочее время. Ревьюер должен проверить, какие lock берёт DDL-операция и сколько времени она может выполняться на production-объёме данных.

Добавление `NOT NULL` колонки выполняется безопасно: сначала nullable колонка, затем backfill батчами, затем validation constraint или отдельный шаг с короткой блокировкой. Один большой update всей таблицы в миграции является риском.

Индексы на больших таблицах создаются конкурентно, если СУБД это поддерживает. Для PostgreSQL используется `CREATE INDEX CONCURRENTLY`, а миграционный инструмент должен уметь выполнять такую операцию вне транзакции.

Удаление колонки или изменение формата данных требует периода совместимости. Сначала код перестаёт писать старое поле, затем выполняется deploy, потом поле удаляется отдельной миграцией после проверки, что старые версии приложения больше не работают.

Backfill должен иметь batch size, паузы или throttle, чтобы не заблокировать пользовательские запросы. Для критичных таблиц нужен план rollback и SQL для мониторинга lock wait, времени выполнения и количества обработанных строк.
