# API Contract Review

Ревью API начинается с совместимости контракта. Новый endpoint должен иметь явную request schema, response schema, коды ошибок и ограничения размеров входа. Нельзя принимать произвольный dict без валидации, если endpoint публичный или вызывается другим сервисом.

Backward incompatible изменения требуют версии API, feature flag или миграционного периода. Если поле ответа переименовано или меняет тип, ревьюер должен спросить, какие клиенты уже зависят от старого контракта.

Ошибки должны быть машинно-читаемыми. Хороший формат содержит стабильный `code`, человекочитаемый `message` и, при необходимости, список field-level details. Нельзя заставлять клиента парсить свободный текст ошибки.

Идемпотентность важна для POST/PUT операций, которые могут повториться из-за retry. Если операция создаёт ресурс, нужен idempotency key, естественный unique constraint или явная защита от дублей.

Для streaming API нужно проверить формат событий, завершение потока, обработку client disconnect и поведение при ошибке LLM или downstream-сервиса. Поток не должен зависать без финального события или закрытия соединения.
