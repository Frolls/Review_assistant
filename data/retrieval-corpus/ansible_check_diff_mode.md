# Ansible check mode и diff mode

Источник: https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_checkmode.html

Check mode запускает playbook как симуляцию без применения изменений на managed nodes. Модуль, поддерживающий check mode, сообщает ожидаемый change. Модуль без поддержки может ничего не выполнить и ничего не вернуть, поэтому успешный dry run не доказывает корректность каждой задачи.

Playbook запускается с `ansible-playbook ... --check`. Этот прогон полезен для конфигурационных tasks, package state и других декларативных операций. Команды, зависящие от результата предыдущего реально изменяющего task, могут вести себя иначе, потому что симулированный ресурс ещё не существует.

`check_mode: true` принудительно выполняет конкретную task в режиме проверки даже при обычном запуске. Это можно применять для зондирования возможного изменения с `register`. `check_mode: false` разрешает реальное выполнение внутри общего dry run и требует повышенного внимания: такая task способна изменить систему вопреки ожиданию оператора.

Magic variable `ansible_check_mode` позволяет пропустить или адаптировать задачу. Условие должно быть обосновано. Простое исключение всех сложных tasks делает dry run зелёным, но бесполезным; лучше улучшить поддержку check mode или явно документировать ограничение.

Diff mode показывает before/after для модулей, которые его поддерживают, особенно template и file operations. Его можно применять отдельно или вместе с `--check`. Сочетание помогает увидеть не только факт будущего change, но и содержимое предполагаемой правки.

Diff может выводить чувствительные данные. Для template с secrets используется `diff: false`, даже если файл защищён permissions. Оператор ограничивает запуск одним host или узкой группой, поскольку большой diff создаёт шум и повышает риск утечки в CI logs.

На ревью проверяется поддержка check mode у custom module, command wrapper и tasks с registered variables. Если последующая condition зависит от output команды, которая не запускается в check mode, результат симуляции может отличаться от normal run.

Удаление файла, миграция, управление пользователями и изменение firewall должны иметь проверенный dry-run path. Однако check mode остаётся прогнозом, а не транзакцией и не заменяет staging, backup, health check и rollback для опасных операций.

Для role полезен тест минимум в три этапа: normal converge, второй idempotence run и `--check --diff`. Второй запуск должен показывать отсутствие необоснованных changes, а dry run после converge — отсутствие ожидаемого drift.

Если task всегда changed в check mode, проверяется, может ли модуль определить текущее состояние или нужен `changed_when`. Подавление change без сравнения состояния делает отчёт красивее, но скрывает реальную проблему идемпотентности.

CI должен ограничивать и защищать diff artifacts. Секреты не должны попадать в console output, а inventory и credentials для проверки выбираются отдельно от production. Результат check mode сохраняется как диагностический сигнал, а не как единственное разрешение на deploy.
