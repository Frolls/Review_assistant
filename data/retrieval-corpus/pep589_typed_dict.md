# PEP 589: TypedDict для словарей фиксированной формы

Источник: https://peps.python.org/pep-0589/

TypedDict описывает словарь с заранее известным набором строковых ключей и отдельным типом каждого значения. Во время исполнения такой объект остаётся обычным `dict`; конструкция предназначена для статической проверки и не выполняет runtime validation входного JSON.

TypedDict подходит для существующего dictionary-shaped контракта: payload внешнего API, legacy JSON, конфигурация или промежуточное представление, которое нельзя сразу заменить классом. Он точнее `dict[str, Any]`, потому что анализатор знает допустимые ключи, обязательность и тип доступа по каждому ключу.

Обязательные и необязательные ключи — это не то же самое, что значение `T | None`. Необязательный ключ может отсутствовать, а обязательный ключ со значением Optional должен присутствовать, но может содержать `None`. Ревьюер проверяет, какую семантику действительно использует код: `key not in payload` и `payload[key] is None` могут означать разные состояния.

Современный стиль позволяет помечать отдельные поля `Required` и `NotRequired`; параметр `total=False` делает все поля по умолчанию необязательными. Широкий `total=False` может скрыть ошибку модели, если большинство ключей фактически требуется. Лучше выражать обязательность каждого контракта явно и не переносить partial update schema в read model.

TypedDict поддерживает наследование для расширения набора полей. Оно должно отражать совместимые формы данных, а не использоваться только ради сокращения нескольких строк. Переопределение поля несовместимым типом или изменение его обязательности нарушает безопасную подстановку.

Операции со словарём ограничены статической моделью. Доступ по произвольной строковой переменной, удаление обязательного ключа или запись значения другого типа должны вызывать диагностику. Если код массово обходит эти ограничения через `cast` и ignore, фактическая структура, вероятно, слишком динамична для выбранного TypedDict.

Для входных данных из сети, очереди или файла одного TypedDict недостаточно. Сначала требуется parser или validator, который проверит наличие ключей и типы во время исполнения. После успешной проверки значение можно безопасно передать в типизированную внутреннюю часть приложения.

Dataclass или Pydantic-модель предпочтительнее, когда нужны методы, инварианты, преобразование типов, aliases, сериализация или runtime validation. TypedDict сохраняет совместимость с обычным dict и минимальный runtime overhead. Выбор зависит от границы системы, а не от личного вкуса.

При публичном API изменение обязательного ключа, его типа или значения имеет последствия для producer и consumer. Добавление необязательного поля обычно мягче, но старые клиенты всё равно не должны предполагать исчерпывающий набор ключей. Ревьюер проверяет миграционный порядок и обратную совместимость сериализации.

TypedDict полезен для постепенной типизации. Можно сначала описать наиболее устойчивые поля legacy payload, затем сузить `Any` и добавить validation на внешней границе. Миграция должна уменьшать динамическую область, а не создавать alias, который лишь переименовывает `dict[str, Any]`.

В тестах следует проверять runtime validation отдельно от статических типов. Type checker ловит неправильный ключ в коде, а unit test подтверждает поведение на неполном или повреждённом JSON. Эти проверки дополняют друг друга и не являются взаимозаменяемыми.
