# Ansible playbooks: идемпотентность и структура задач

Источники:

- https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_intro.html
- https://docs.ansible.com/projects/lint/rules/no-changed-when/

Playbook описывает желаемое состояние управляемых узлов. Повторный запуск идемпотентной автоматизации не должен менять итоговое состояние, если входные данные и окружение не изменились. На ревью проверяется не только успешный первый запуск, но и корректный статус `changed` при повторном выполнении.

Следует предпочитать специализированный модуль Ansible произвольной команде. Модули package, service, user, file, template и repository понимают состояние ресурса и обычно поддерживают idempotency и check mode. `shell` или `command` оправданы, если подходящего модуля нет либо вызываемый инструмент сам предоставляет надёжную декларативную операцию.

Для `command` и `shell` нужно явно определить, когда задача меняет систему. Параметры `creates` и `removes` позволяют пропустить команду по состоянию файла. Более сложный случай использует `register` и выражение `changed_when`, основанное на return code или output. Без этого задача может сообщать change при каждом deploy и без причины запускать handlers.

`changed_when: false` допустим для чистой диагностической команды, которая гарантированно ничего не изменяет. Безусловный `changed_when: true` почти всегда подозрителен: он разрушает полезность отчёта и вызывает notify при каждом запуске. Условие должно описывать наблюдаемый факт изменения, а не подавлять lint rule.

Имена play и task должны описывать желаемый результат и быть уникальными в пределах понятного контекста. Хорошее имя видно в output и помогает определить место сбоя без чтения YAML. Общие имена вроде «Configure service» затрудняют поиск, особенно внутри нескольких roles.

Следует использовать полное имя коллекции модуля, например `ansible.builtin.template`. FQCN делает источник модуля явным, избегает конфликта имён и упрощает переход между версиями коллекций. Короткое имя может быть локальным соглашением, но оно не должно создавать неоднозначность.

Аргументы модуля записываются в native YAML form, а не одной строкой key=value. Структурная форма лучше читается в diff, поддерживает вложенные параметры и меньше зависит от особенностей quoting. Булевы значения и file modes должны быть однозначны; mode безопаснее задавать строкой вроде `'0644'`.

Переменные должны иметь понятную область и единый стиль имён. Inventory-specific hostnames, credentials и environment values не встраиваются в reusable role. Default values хранят безопасные переопределяемые настройки, а обязательный параметр проверяется явно до выполнения опасных задач.

Package version или repository channel фиксируется, если неконтролируемое обновление может сломать production. Простое `state: latest` в критическом окружении требует обоснования и плана проверки. Обновление зависимости и изменение конфигурации полезно разделять, чтобы rollback оставался предсказуемым.

Privilege escalation применяется на минимальном уровне. Если `become: true` установлен для всего play, любая новая задача автоматически получает повышенные права. На ревью безопаснее видеть escalation рядом с конкретной операцией, которой оно действительно необходимо.

Template и copy должны задавать owner, group и mode там, где defaults окружения недостаточно надёжны. Секретный файл требует ограниченного режима. Изменение template обычно уведомляет handler, а не перезапускает сервис немедленно отдельной всегда изменяющейся задачей.

Перед reload конфигурация должна пройти проверку, если модуль поддерживает `validate`. Команда в validate получает временный файл и выполняется до замены целевого. Для nginx, sudoers и других чувствительных конфигураций это предотвращает установку синтаксически неверного файла.

Удаление файлов, изменение firewall, миграция данных и рестарт сервиса требуют особого внимания к scope. Task должен ограничивать target, иметь понятный condition и не зависеть от случайного порядка host iteration. Для опасной операции полезны serial rollout и отдельная проверка успешности.

Tags не должны быть единственным механизмом корректности: playbook без специальных флагов должен иметь безопасное и понятное поведение. Динамические include и conditions проверяются для всех существенных веток. Ревьюер оценивает normal run, повторный run и ограниченный запуск по tags.

Секреты, tokens и passwords не записываются в task body, defaults или открытый inventory. `no_log: true` уменьшает риск вывода значения, но не является хранилищем секретов и усложняет диагностику; его используют точечно вместе с Vault или внешним secret manager.
