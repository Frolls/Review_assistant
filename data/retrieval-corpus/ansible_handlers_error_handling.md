# Ansible handlers и обработка ошибок

Источники:

- https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_handlers.html
- https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_error_handling.html

Handler выполняет операцию только после уведомления задачей со статусом changed. Типичный случай — restart или reload сервиса после изменения конфигурации. Если несколько задач уведомили один handler, он обычно выполняется один раз в конце соответствующей секции play, что предотвращает лишние перезапуски.

Имя в `notify` должно однозначно соответствовать handler или его `listen` topic. Несколько handlers могут слушать одну тему, например `restart web services`. Topic уменьшает связь task с конкретным именем, но переименование и область видимости должны проверяться, чтобы уведомление не стало молча неработающим.

Handler не запускается, если notifying task вернула ok. Поэтому корректность зависит от честного changed status модуля или `changed_when`. Task с `changed_when: true` перезапускает сервис на каждом прогоне; task с ошибочным `changed_when: false` не применит необходимый reload после реального изменения.

По умолчанию handlers выполняются после завершения tasks. `meta: flush_handlers` запускает уже уведомлённые handlers раньше и оправдан, если последующие задачи требуют новой конфигурации. Частые flush разрушают batching и могут вызвать несколько restart, поэтому необходимость должна следовать из порядка операций.

Если task на host завершилась ошибкой позже notifying task, handler для этого host по умолчанию может не выполниться. Это способно оставить обновлённый конфигурационный файл без соответствующего restart. `force_handlers` меняет поведение, но не лечит недоступный host или падение самого handler; решение требует анализа риска и rollback.

`ignore_errors` продолжает выполнение после определённых failed tasks, но не игнорирует все виды ошибок и часто скрывает нарушение инварианта. Его нельзя добавлять только ради зелёного pipeline. Ожидаемый ненулевой return code лучше выразить через `failed_when`, а альтернативный flow — через block, rescue и always.

`failed_when` определяет доменную ошибку по return code, stdout, stderr или другим полям registered result. Список условий объединяется неявным AND. Если ошибка наступает при любом из нескольких условий, используется строковое выражение с явным OR; иначе task может ошибочно считаться успешной.

`changed_when` имеет аналогичную семантику списков. Условие должно опираться на зарегистрированный результат и не использовать шаблонные delimiters `{{ }}` внутри expression. Warning о delimiters часто показывает смешение Jinja rendering и условного выражения.

Block группирует задачи с общими directives и позволяет задать `rescue` для восстановления после failure и `always` для обязательной очистки или отчёта. Rescue не должен превращать любой дефект в success: после компенсации может потребоваться явный fail с сохранённым контекстом.

Unreachable host отличается от failed task. `ignore_unreachable` и `meta: clear_host_errors` применяются только при осознанной модели восстановления связи. Автоматическое продолжение после потери host может создать частично развернутое окружение.

Для coordinated rollout важны `any_errors_fatal`, `max_fail_percentage` и `serial`. Они определяют, остановит ли ошибка дальнейшие batches. На ревью проверяется, соответствует ли policy допустимому числу недоступных узлов и не продолжится ли несовместимое обновление после отказа первой группы.

Shell pipeline может вернуть код только последней команды и скрыть ранний failure. Если shell необходим, включается корректная обработка pipeline либо команда перестраивается на модули и отдельные tasks. Проверка только наличия текста в stdout без return code часто недостаточна.

Handler сам является task и нуждается в идемпотентности и корректной обработке ошибок. Restart должен ссылаться на правильное service name, учитывать platform differences и не игнорировать failed state. Если доступен reload без downtime, выбор restart требует обоснования.

В PR с template, notify и handler ревьюер отслеживает полную цепочку: действительно ли template сообщает changed, совпадает ли notify, когда выполнится handler, что произойдёт при промежуточной ошибке и проверяется ли здоровье сервиса после применения.
